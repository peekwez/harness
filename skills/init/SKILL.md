# /harness:init

Run the scaffold:

!`"${CLAUDE_PLUGIN_ROOT}/bin/harness" init`

Then report to the user, verbatim, the provenance rule the command printed:
authored files are written by humans and never regenerated; derived files are
regenerated by hooks — hand-editing one is a bug.

Rules:

- If the command refuses because a substrate exists, do NOT delete anything.
  Ask the user whether they intend an upgrade of the existing substrate to
  the installed plugin (`"${CLAUDE_PLUGIN_ROOT}/bin/harness" upgrade`:
  schema migration, merge drivers, the vendored CI engine under
  `.harness/engine/` and the `harness-verify` workflow) and only run it on
  explicit confirmation. Tell them to commit `.harness/engine/` and the
  workflow afterwards.
- The scaffold vendors the engine into `.harness/engine/` so the CI
  workflow is self-contained — it must be committed with the rest of the
  substrate, and it is derived (never hand-edited; `upgrade` refreshes it).
- After scaffolding, list which language packs were enabled and tell the user
  to edit `.harness/config.yaml` (authored) if the detection missed one.
- Tell the user what the scaffold contains: `.harness/registry.jsonl` holds
  the standard abstraction slots (config, logging, errors, telemetry — all
  `planned`); `.harness/decisions.jsonl` and `.harness/backlog.jsonl` start
  empty. Nothing needs hand-editing — Phase 0 (`/harness:architect`) fills
  decisions, and `/harness:backlog` appends slices via the CLI. The
  author-gate blocks until every registry domain has a decision row.
- Next step in the workflow: `/harness:architect`.
