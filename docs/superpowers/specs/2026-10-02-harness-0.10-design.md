# Harness 0.10 design: explore first, verify first, leaner context

- Status: draft for review
- Date: 2026-10-02
- Issues: peekwez/harness #2 to #9 (tracker: #9)
- Branch: `release/0.10`
- Written in STE-80: short sentences, one action per step, active voice, one name per concept.

## 1. Goal

Harness 0.10 does three jobs: it records **decisions**, it **proves** behavior, and it keeps actions **safe**. It stops controlling what the agent reads.

Success means:

1. A new design starts with a quick toy. Each big decision cites what the toy showed.
2. Each slice proves that its tests fail before it writes code. Close checks that each statement has a test.
3. Always-on context is smaller and harness reports its cost.
4. Text for humans is short and plain. A tool checks it.
5. A technical reader can learn from one website what harness does, what it does not do, and how to change it.

## 2. Why: what changed

Harness 0.9 assumed that agents cannot find context, wander out of scope, and hand-edit derived files. Current models read code with search and file reads at low cost. Claude Code already requires a file read before an edit. The consumer repo (astralabs, 0.9.4) shows the cost of the old assumptions:

- Path-only G3 non-goals: 46 overrides vs 45 firings.
- G5: 12 overrides vs 1 firing.
- Campaign mode: 0 dispatches.
- Shadows: 3.0 MB, 90% not interfaces. One false G7 block after a docs build.
- Slice context injection: about 2.4k tokens on every prompt. The 9,500-character clip cut the decision rows.
- After 13 closed slices, a whole-repo review found 11 defects. Tests often checked the wrong object.

The risks that remain are: decisions made without evidence, tests that prove nothing, unsafe actions, and text that humans cannot read fast.

## 3. Decision log

Each record uses the decision-card format from section 5.2. "Chosen" is the option the human approved on 2026-10-02.

### D-0.10-01: How much context-policing machinery to remove

- **Chosen:** re-center. Remove G2, G4, G7, committed shadows and per-prompt injection. G3 scope and G5 become advisory.
- **Solves:** the false blocks and token cost measured in section 2. Example: a docs build no longer blocks a session.
- **Trade-off:** a breaking release. `harness upgrade` must migrate each repo.
- **1st order:** about 1,000 engine lines go. Fewer gates fire.
- **2nd order:** close becomes the main place where harness blocks.
- **3rd order:** harness becomes easier to explain, adopt and extend.
- **Undo cost:** medium. The code stays in git history.
- **Rejected:** "trim as issued" (keeps the wrong assumptions); "re-center plus strict mode" (keeps code no user needs).

### D-0.10-02: Memory

- **Chosen:** harness manages only shared memory. Personal agent memory stays with Claude Code, unchanged.
- **Solves:** team facts get an owner and a record of who promoted them. Example: `harness memory promote` copies a fact into `.claude/memory/shared/` with `promoted_by` and `promoted_at`.
- **Trade-off:** "who wrote this" is solved only for shared facts.
- **1st order:** `.harness/memory/` and `harness memory write|flush|compact` go. No hook rewrites personal memory.
- **2nd order:** personal notes and client context never reach git.
- **3rd order:** `shared/` stays small, because a human chose each entry.
- **Undo cost:** low.
- **Rejected:** contributor folders committed (nobody's agent reads them; privacy risk); contributor folders gitignored (no gain over Claude Code's default); harness owns all memory.

### D-0.10-03: How to enforce verification first

- **Chosen:** record red at slice start, check at close. An edit before the red record gives a one-line advisory.
- **Solves:** tests that pass before the code exists. Example: a slice whose suite is green at start cannot close without a recorded reason.
- **Trade-off:** an agent can still edit source before the red record. Close catches it.
- **1st order:** `harness slice start` runs the acceptance suite once.
- **2nd order:** each slice stores evidence that its tests could fail.
- **3rd order:** the "wrong object" defect class from astralabs becomes visible at close.
- **Undo cost:** low.
- **Rejected:** block all edits until red (extra friction on each slice); execute mutants at close (slow; needs a mutation format).

### D-0.10-04: Docs site hosting

- **Chosen:** mkdocs-material, built by GitHub Actions, published to GitHub Pages on peekwez/harness.
- **Solves:** one public URL for evaluators.
- **Trade-off:** the docs build must pass in CI.
- **1st order:** README drops to under 300 lines.
- **2nd order:** the workflow runs only on peekwez. The origin push also reaches goodwork-eng, so the job has a repository guard.
- **3rd order:** the site becomes the place where people send feedback.
- **Undo cost:** low.

### D-0.10-05: Commit shadows or not

- **Chosen:** shadows are a gitignored cache, built lazily.
- **Solves:** repo weight, diff noise and G7 false blocks. Example: a change in `site/` changes no tracked file.
- **Trade-off:** CI rebuilds shadows when G5 or G6 needs them. This adds seconds.
- **1st order:** G7 is deleted.
- **2nd order:** two machines with different tree-sitter versions can build different shadows. `doctor` reports the version.
- **3rd order:** PRs lose shadow diffs. G6 drift acknowledgements become the only record of interface change, so G6 stays blocking.
- **Undo cost:** low.

### D-0.10-06: Resolver budget

- **Chosen:** remove the `resolver.budget_tokens` setting. Use one constant, `MAX_INJECTION_CHARS = 9000`, with a fixed priority order.
- **Solves:** a budget that did not match the clip. Example: a user cannot set 20,000 tokens and lose decision rows without notice.
- **Trade-off:** no per-repo tuning.
- **1st order:** the docstring-drop and module-drop logic goes.
- **2nd order:** over-cap context is a visible finding: split the slice or shorten its rows.
- **3rd order:** `backlog` warns at plan time when a slice's cited rows do not fit.
- **Undo cost:** low.

### D-0.10-07: How a test links to a statement

- **Chosen:** a comment in the test: `verifies: V-orders-3  kills: commit before rollback check`.
- **Solves:** the link moves with the test, in any language.
- **Trade-off:** a typo breaks the link. `compile` and close report unknown IDs.
- **1st order:** no mapping file.
- **2nd order:** the `kills:` text is the mutant record.
- **3rd order:** a coverage page on the docs site can list statements and their tests.
- **Undo cost:** low.

### D-0.10-08: STE-80 checker

- **Chosen:** a built-in `harness lint-text`.
- **Solves:** one deterministic check for skills, docs, decision rows and glossary terms. No new dependency.
- **Trade-off:** it does not detect passive voice or meaning.
- **1st order:** about 150 lines of Python.
- **2nd order:** the glossary becomes enforceable.
- **3rd order:** consumer repos can run it on their own ADRs.
- **Undo cost:** low.
- **Rejected:** Vale (external binary); guidance only (drifts).

### D-0.10-09: Contracts

- **Chosen:** remove contracts from core.
- **Solves:** no unused `contracts/api.yaml`, no stub generation, no contract lint.
- **Trade-off:** a team that wants OpenAPI checks adds a `gates.extra` gate or a linter in CI.
- **1st order:** the `init` scaffold, `compile` stub generation, the `verify` lint and the `contract-first` skill go.
- **2nd order:** "use a contract as the seam" becomes a decision card in architect.
- **3rd order:** the docs site shows a `gates.extra` recipe for contracts.
- **Undo cost:** low.

### D-0.10-10: Other-host adapters

- **Chosen:** leave them in `adapters/`.
- **Solves:** nothing to do. The Claude Code plugin does not load them, so they cost no tokens.
- **Trade-off:** a larger repo on disk.
- **1st order:** no work.
- **2nd order:** the conformance tests keep them correct in one CI.
- **3rd order:** the docs site can show harness as host-agnostic.
- **Undo cost:** none.

### D-0.10-11: Telemetry

- **Chosen:** per-event rows stay local in `.harness/cache/events.jsonl`. Close writes one committed summary row per slice to `.harness/slice-metrics.jsonl`.
- **Solves:** keeps the evidence that found unused features, without git noise. Example row: gates fired, overrides, maximum injection size, compactions, red-before-green result.
- **Trade-off:** event detail stays on the machine where it happened.
- **1st order:** most of the 470 lines of crash-safe flush, quarantine and archive code go.
- **2nd order:** `harness status` reads summaries.
- **3rd order:** each release can show if harness grew or shrank.
- **Undo cost:** low.
- The `telemetry.compaction_is_defect` rule goes. Compactions are counted, not flagged.

### D-0.10-12: Is explore required

- **Chosen:** required for new designs. `architect` refuses to start from nothing unless `explore/` is frozen, `--from-spec` is given, or `--skip-explore "<reason>"` is recorded.
- **Reason (human):** explore exists to test ideas fast and to give decisions evidence. Without it, design goes straight to decisions without evidence.
- **Solves:** decisions made before anything runs.
- **Trade-off:** one more step, or a one-line reason to skip.
- **1st order:** each design has a toy or a recorded reason for no toy.
- **2nd order:** skip reasons appear in slice metrics.
- **3rd order:** existing projects are not affected. They can add `VERIFY.md` at any time.
- **Undo cost:** low.

### D-0.10-13: Reference docs

- **Chosen (default, confirm in review):** generated at build time from the code.
- **Solves:** the reference cannot drift. Example: removing G7 removes it from the gates page in the same PR.
- **Trade-off:** a build hook of about 100 lines.
- **1st order:** CLI, gates, config keys and finding codes come from code.
- **2nd order:** docstrings and finding text become user-facing.
- **3rd order:** a contributor updates the docs by changing the code.
- **Undo cost:** low.

### D-0.10-14: Skills 18 to 11

- **Chosen:** the merge map in section 10.
- **Solves:** skill listing cost and overlap.
- **Trade-off:** users of removed skill names must use the new name.
- **Undo cost:** low.

## 5. Explore and design rigor

### 5.1 Principle

Skill level changes how much the agent explains. It never changes what the agent checks.

### 5.2 The decision card

Each big decision uses one format. Big decisions are stores, transports, tiers, seams, trust boundaries, and anything that is hard to undo.

```markdown
## D-E3: <question in plain words>

**Why now:** <one sentence>
**Evidence:** <what the toy showed: file, command or observation> | no evidence: <reason>

### Option A: <name> (recommended)
- Solves: <plain words>
- Example: <concrete case>
- Trade-off: <what you give up>
- 1st order: <direct effect>
- 2nd order: <effect of the effect>
- 3rd order: <longer-term effect>
- Undo cost: low | medium | high, <why>

### Option B: <name>
<same fields>

**Would change it:** <fact that would change the recommendation>
**Chosen:** A | B | parked
**Reason:** <the human's reason, in their words>
```

Rules:

1. Each field is one or two sentences.
2. The human can answer: an option, "explain more about X", or "not sure, park it".
3. "Park it" moves the question to `OPEN.md` with an owner and a trigger.
4. The agent never treats a vague reply as a choice.

### 5.3 Explore flow

1. **Calibrate.** The agent asks one question for each area that matters to this app: new to it, used it, or designed it. It adapts from what it observes. It keeps this in its own personal memory. Harness does not store it.
2. **Frame.** The agent writes back the problem, users, constraints and success criteria. It marks what the human said and what it assumed. The human corrects it.
3. **Toy.** The agent builds a quick toy in `explore/`. Speed is the goal, not quality.
4. **Cards.** The agent writes a card for each big decision. Each card cites toy evidence.
5. **Verify list.** The agent writes `VERIFY.md` statements for each feature.
6. **Challenge.** The red-team pass and the Claude/Codex design review attack each card's "Would change it" line.
7. **Freeze.** The human runs `harness explore --freeze`.

### 5.4 Files

| File | Owner | Content |
|---|---|---|
| `explore/` code | agent | the toy, any structure |
| `explore/DECISIONS.md` | human signs | decision cards |
| `explore/VERIFY.md` | human signs | statements: `V-<feature>-<n>: <statement>` |
| `explore/OPEN.md` | agent | parked questions: question, owner, trigger |

### 5.5 Commands

- `harness explore` creates the folder and the three files from templates.
- `harness explore --freeze`:
  1. checks that each card has all fields;
  2. checks that each `Chosen` is A, B, C or parked;
  3. checks that each statement ID is unique and matches `V-[a-z0-9-]+-[0-9]+`;
  4. writes `frozen_by` (git identity) and `frozen_at_commit` into `DECISIONS.md` front matter.
- `harness architect --from-explore` writes one decision row per chosen card. The row answer is 150 words or fewer. The full card goes into an ADR that the row cites. Architect does not re-ask a question that a card answers.
- `harness architect` with no `--from-explore`, no `--from-spec` and no `--skip-explore "<reason>"` refuses to start. `--skip-explore` records the reason in the working document and in slice metrics.

### 5.6 Gates and explore

- New config key `gates.exempt_paths` (a list of path prefixes). Default: `.harness/ adr/ .github/ tests/ docs/ .claude/ explore/`. G3 and G5 read it. It replaces the hardcoded `SUBSTRATE_PREFIXES` and the G5 tuple.
- **G9 explore-isolation:** a touched file outside `explore/` whose shadow imports resolve to a file under `explore/` is a block. It runs at `post_change` and `unit_complete`, and in `harness verify`.
  - Python resolution: module ids that start with `explore.`
  - TypeScript and JavaScript: relative or absolute import paths that resolve under `explore/`
  - Go and Rust: import paths that contain the `explore` package directory of this repo

## 6. Verification first

### 6.1 Statements

- Statements come from `explore/VERIFY.md`. Without explore, they come from the architect verification matrix with the same ID format.
- `compile` writes `.harness/verify.jsonl`. One row per statement: `{id, feature, statement, source}`.
- `backlog add --verifies V-x-1,V-x-2` stores `verifies` on the slice row. `backlog` reports statements that no slice owns.

### 6.2 Test links

A test links to a statement with a comment, in any comment syntax:

```python
# verifies: V-orders-3  kills: commit happens before the rollback check
def test_rollback_leaves_no_event_row(): ...
```

- `verifies:` names one or more IDs, separated by commas.
- `kills:` names the bug that the test must catch. This is the mutant record. Harness does not execute it.
- `compile` and close report a `verifies:` ID that is not in `verify.jsonl`.

### 6.3 Red record

`harness slice start` runs the acceptance suite of the slice once, with the configured runner.

- The suite must exit non-zero.
- Harness writes `.harness/verification/<slice>.json`: `{slice, commit, ran_at, exit_code, output_tail, per_test?}`. The file is committed.
- With `acceptance.junit: true`, the runner writes JUnit XML, and harness records the result of each test.
- A suite that passes at start is recorded as `green_at_start: true`.
- Before a red record exists, an edit to a non-test file gives one advisory line: `No red record for slice <id>. Run: harness slice start <id>.`

### 6.4 Close checks

Close blocks when one of these is false:

1. The acceptance suite is green.
2. The regression suite of closed slices is green.
3. A red record exists. If `green_at_start` is true, an override with a reason is recorded (example: a pure refactor slice).
4. Each statement in the slice's `verifies` has at least one test with a `verifies:` comment.
5. Each such test has a `kills:` text.
6. Each G6 drift has an acknowledgement.

## 7. Context and shadows

### 7.1 Shadow cache

- Location: `.harness/cache/shadows/`. The whole `.harness/cache/` folder is gitignored.
- One accessor: `shadow_for(root, path, config) -> dict | None` in `engine/extractor/engine.py`. It returns the cached shadow when source hash, extractor version, language and import context match. Otherwise it rebuilds and stores it. It returns `None` for a file outside scope.
- G5, G6, review layer 0, `registry.public_symbols` and the resolver all use `shadow_for`.
- The registry `shadow` field is removed. It is derived from `source`.
- `harness extract --all` only warms the cache.

### 7.2 Scope

A file is in scope when all of these are true:

1. `git ls-files --cached --others --exclude-standard` lists it. This applies `.gitignore`.
2. It does not match the default exclusions:
   - tests: `tests/`, `*/tests/`, `test_*.py`, `*_test.py`, `*_test.go`, `*.test.ts`, `*.spec.ts`, `conftest.py`
   - generated or minified files: `*.map`, `*.min.*`
   - media and archives
   - files over 1 MB
   - binary files (a NUL byte in the first 8 KB)
3. It does not match `shadows.exclude`, unless `shadows.include` matches it.

`shadows.include` and `shadows.exclude` are lists of globs in `config.yaml`.

### 7.3 Removed

- G2, G4, G7.
- The close step "derived artifacts".
- Shadow regeneration in `merge-slice`.
- The `verify` check that built registry entries have a shadow file.
- The Stop hook keeps one job: record `uses` edges for touched files.

### 7.4 Context injection

- The resolver injects at SessionStart and on the first UserPromptSubmit after a slice binding.
- The injection has blocks. The sidecar stores a hash for each block per session. On a later prompt, only changed blocks are sent. No change means nothing is sent.
- PreCompact clears the stored hashes. The next prompt injects once again.
- Priority order:
  1. gate findings
  2. decision rows that the slice cites
  3. non-goals
  4. slice card: goal, statements, predicted files
  5. module pointers: `harness resolve --module <id>`
- Cap: `MAX_INJECTION_CHARS = 9000`. When the blocks do not fit, harness cuts from the lowest priority. Each cut block becomes a one-line pointer. A cut adds the advisory finding `CONTEXT_OVER_CAP`.
- The adapter clip stays at 9,500 characters as a safety net.
- Durable memories are not injected.
- `harness resolve <slice>` from the CLI has no cap.

### 7.5 Cost report

`harness status` prints the always-on cost per source:

- skill listing
- agent listing
- `AGENTS.md`
- shared memory index
- last injection size

Each is in characters and estimated tokens.

### 7.6 AGENTS.md

`templates/agents-md.md` is 50 lines or fewer. It keeps:

- the binding rules, one line each;
- the autonomy stop conditions;
- the workflow command list;
- the STE-80 line.

It replaces the D-014 text, the Codex section and the gate glossary with one-line pointers to skills.

## 8. Shared memory

- Folder: `.claude/memory/shared/`, committed. It holds `MEMORY.md` and one file per fact.
- The `CLAUDE.md` template imports `@.claude/memory/shared/MEMORY.md`.
- `harness memory promote <file> | --text "<fact>"` copies a fact into `shared/`. It adds front matter `promoted_by` (git identity) and `promoted_at`. It adds one line to `shared/MEMORY.md`, 120 characters or fewer.
- A PreToolUse rule blocks agent Write and Edit calls into `.claude/memory/shared/`. The message names `harness memory promote`.
- The permit layer never auto-approves `harness memory promote`. A human approves each promotion.
- At close, the close-slice skill lists personal memory files changed since the slice started and asks the human: "Promote any to shared?"
- `doctor` warns when `shared/MEMORY.md` has more than 40 entries.

## 9. Writing for humans (STE-80)

### 9.1 Rules

1. Short sentences: 25 words or fewer in steps and messages.
2. One action per step.
3. Active voice with a named subject.
4. One name per concept, from the glossary.

### 9.2 Where

| Surface | Change | Check |
|---|---|---|
| `AGENTS.md` | one STE-80 line; pointer to `skills/harness/ste80.md` | template test |
| Findings | `make_finding(..., fix=)`; message = rule, what is wrong, file; 25 words or fewer; detail in a catalog | test over every gate fixture |
| Finding detail | `engine/findings.py` maps code to explanation; `harness gates explain <CODE>` | test: every emitted code has a catalog entry |
| Skills and agents | numbered steps; rules, not history | skill lint test calls `lint-text` |
| Decision rows | `compile` warns when an answer is over 150 words | compiler test |
| Decision cards | fields of one or two sentences | `explore --freeze` |
| Review findings | `summary` and `failure_scenario` in STE-80 | reviewer agent instructions |
| Glossary | `init` writes `docs/glossary.md`: `term — definition (not: synonym, synonym)` | review layer 0 flags synonyms in a diff (advisory) |
| Docs site | STE-80 | `lint-text` in docs CI |

### 9.3 `harness lint-text <paths>`

It checks:

- sentence length over 25 words in list items and numbered steps, and over 35 words in prose;
- words from a banned list (examples: utilize, leverage, simply, robust, "in order to");
- glossary synonyms from `not:` lists.

It prints `file:line: rule: text`. It exits non-zero on any finding. It skips code blocks and front matter.

## 12. Upgrade (schema 1 to 2)

**Requirement:** `harness upgrade` brings any existing 0.8.x or 0.9.x harness repo fully onto 0.10. After it runs, the repo follows every change in this spec, and `harness verify` and `harness doctor` pass. No change in 0.10 depends on a manual step. Rules:

- **Complete.** Every 0.10 change that touches consumer files has an upgrade step. A workstream PR that changes consumer-visible substrate without an upgrade step fails review.
- **Chained.** Upgrade runs the existing 0.8 and 0.9 migrations first, then the 0.10 steps. A 0.8 repo reaches 0.10 in one run.
- **Idempotent.** A second run changes nothing and reports "already on 0.10".
- **Safe.** `--dry-run` prints the plan and changes nothing. Each step that moves or deletes files asks first. `--yes` accepts all prompts, for CI.
- **Verified.** Upgrade ends with `harness doctor` and `harness verify`, and prints their result. A failure names the step and the fix.
- **One commit.** Upgrade stages its changes and proposes one commit: `harness: upgrade to 0.10`.

`harness upgrade` runs these steps.

1. Untrack `.harness/shadows/`, delete it, and add `.harness/cache/` to `.gitignore`.
2. Convert `telemetry.jsonl` and its archive into per-slice rows in `slice-metrics.jsonl`. Delete the old files. Git history keeps them.
3. List `.harness/memory/durable.jsonl` rows. Offer each one for promotion to `shared/`. Then delete `.harness/memory/`.
4. Leave existing `contracts/` files in place. Report that harness no longer checks them.
5. Rewrite `config.yaml`:
   - remove `resolver.budget_tokens`, `resolver.ranking`, `resolver.degrade`, `telemetry.compaction_is_defect` and `ensemble`;
   - add `review.ensemble: false` and `gates.exempt_paths`.
6. Refresh `AGENTS.md` and `CLAUDE.md` when they carry the harness marker. Add the `@.claude/memory/shared/MEMORY.md` import. When a file has no marker, print the lines to add and do not edit it.

## 14. Testing

- Each workstream uses TDD.
- Tests of removed features go in the same PR as the removal.
- The acceptance lines of each issue become tests:
  - a 15-prompt session on one bound slice injects once, then only deltas (#4);
  - over the cap, decision rows survive and pointers replace lower blocks (#4);
  - `templates/agents-md.md` has 50 lines or fewer (#4);
  - after a change under an ignored `site/` folder, no tracked file changes and no gate blocks (#8);
  - a repo with the astralabs layout shadows only `libs/**/src/**` (#8);
  - `ls skills/` lists 11 skills (#5);
  - `harness init` creates no `contracts/` (#5);
  - an agent write into `.claude/memory/shared/` is blocked (#6);
  - every finding message has 25 words or fewer and a catalog entry (#7);
  - `compile` warns on a decision answer over 150 words (#7);
  - a slice with a green suite at start cannot close without an override (#3);
  - a statement with no test blocks close (#3);
  - an import from `explore/` in production code fails G9 (#2);
  - an edit under `explore/` gives no G3 or G5 finding (#2);
  - `architect` with no explore, no spec and no skip reason refuses to start (#2).
  - upgrade fixtures: a 0.8 repo and a 0.9.4 repo (astralabs layout, with committed shadows, telemetry, durable memory, contracts stub and one in-flight slice) upgrade in one run, then `verify` and `doctor` pass;
  - a second upgrade run changes no file;
  - `--dry-run` changes no file;
  - the in-flight slice closes after upgrade without a red record.
- `make test` stays green at the end of each workstream.
